# Weekly Pipeline Operations Guide

Status: operational companion to `docs/weekly-pipeline-design-v0.1.md`.

## 1. GitHub Actions workflow — Weekly pipeline spine

Use:

```text
Actions -> Weekly pipeline spine -> Run workflow
```

Available commands:

### `plan`

Purpose:

- calculate the latest completed weekly issue label;
- calculate Friday 18:00 `America/New_York` cutoff;
- carry forward the latest prior `collection_anchor_at`;
- emit `plan.json` and `plan.md` as an Actions artifact;
- when an anchor exists, generate the issue-specific Grok Trend Sensor Run Instruction and instruction provenance.

No repository write or LLM call occurs.

### `source-intake`

Required input:

```text
issue_id
collector = all | arxiv | github | official
```

Purpose:

- reuse the same issue/cutoff/collection-window calculation as `plan`;
- refuse a requested issue ID that does not match the latest completed cutoff issue;
- collect reproducible discovery inputs from configured arXiv, GitHub Releases, and official news/blog index sources;
- preserve exact HTTP response bytes under collector-specific `raw/` directories;
- emit a separate `summary.json` and `collector-run.json` for downstream screening.

Output artifact:

```text
weekly-source-intake-<issue>
```

The artifact mirrors the eventual repository layout under:

```text
sources/<issue>/collectors/
```

The workflow does not commit collector output automatically. Review/import happens before Raw provenance indexing.

Important: `official` is a configured snapshot collector, not a claim verifier or a complete web search. `github` uses a curated repository watchlist. `arxiv` uses configured categories and a submitted-date window. Candidate-specific verification still happens later.

### `validate`

Required input:

```text
issue_id
```

Targets:

```text
selection
draft
release-candidate
frozen
```

This performs deterministic repository-structure checks and known static hazards. It does not replace claim review, chronology review, TeX compilation or visual review.

### `raw-index`

Required input:

```text
issue_id
```

Purpose:

- scan every file under a `raw/` path inside `sources/<issue>/`;
- compute SHA-256 and byte size;
- refuse to proceed if an already-indexed Raw file was modified or removed;
- add newly discovered Raw files to the index;
- upload generated `raw-index.json` and a report as an Actions artifact.

The workflow does **not** commit the generated index automatically. The initial or changed index should be reviewed before being written to the repository.

### `raw-check`

Required input:

```text
issue_id
```

Purpose:

- compare committed `raw-index.json` against current Raw files;
- fail on modified, removed or unindexed Raw files.

This remains useful for an explicit manual integrity check.

### Automatic `raw-integrity` job

Once an issue has a committed `sources/<issue>/raw-index.json`, normal push/PR CI also verifies Raw integrity automatically.

The workflow is triggered when either of the following changes:

```text
sources/*/raw-index.json
sources/**/raw/**
```

The `raw-integrity` job scans every committed issue baseline and runs `raw_provenance.py check` for each one. A modified, removed, or newly-unindexed Raw file therefore blocks CI even when nobody remembers to run `raw-check` manually.

## 2. Local CLI equivalents

### Plan

```bash
python scripts/weekly_pipeline.py plan
```

### Initialize state

```bash
python scripts/weekly_pipeline.py init --issue-id 2026-W33
```

Initialization refuses to overwrite an existing `pipeline-state.json` unless `--force` is explicitly supplied.

### Run source intake

First write a plan:

```bash
python scripts/weekly_pipeline.py plan --output /tmp/weekly-plan.json
```

Then:

```bash
python scripts/source_intake.py \
  --plan /tmp/weekly-plan.json \
  --collector all \
  --output-root /tmp/survey-intake
```

This performs network access; unit tests mock the HTTP layer and verify Raw-byte preservation/window filtering separately.

### Validate issue state/artifacts

```bash
python scripts/weekly_pipeline.py validate \
  --issue-id 2026-W32 \
  --target frozen
```

### Create/update Raw provenance index

```bash
python scripts/raw_provenance.py \
  --issue-id 2026-W32 \
  update
```

### Verify Raw provenance

```bash
python scripts/raw_provenance.py \
  --issue-id 2026-W32 \
  check
```

## 4. GitHub Actions workflow — Release frozen weekly survey

Release distribution is intentionally separate from editorial build/freeze.

Use:

```text
Actions -> Release frozen weekly survey -> Run workflow
```

Inputs:

```text
issue_id
revision
mode = validate | draft | publish
confirmation = <issue>@<revision>
```

Canonical sequence:

```text
validate -> draft -> human inspection -> publish
```

### Validate example for W32

```text
issue_id      2026-W32
revision      v0.2
mode          validate
confirmation  2026-W32@v0.2
```

`validate` creates no tag/Release. It obtains the exact frozen PDF according to `sources/<issue>/release-manifest.json`, verifies SHA-256, and uploads a validation artifact.

`draft` creates/verifies tag `weekly/<issue>/<revision>`, creates a Draft Release and attaches the verified PDF plus `SHA256SUMS.txt`. Re-running draft mode verifies an existing Draft PDF instead of clobbering it.

`publish` requires the tag and Draft to already exist. It re-verifies the Draft PDF SHA-256 and checksum asset, then publishes the Draft.

See `docs/weekly-release-process.md` for the full policy, including W32's frozen-Artifact exception and future reproducible-build policy.

## 5. Reproducible PDF builds

New `Build weekly survey PDF` runs export:

```text
SOURCE_DATE_EPOCH=<source commit timestamp>
FORCE_SOURCE_DATE=1
```

before LuaLaTeX and upload both `main.pdf` and `main.pdf.sha256`.

This is intended to make future frozen issues byte-reproducible under the same source commit/toolchain. W32 v0.2 predates this policy and therefore releases the exact already-validated Actions artifact instead of assuming a later rebuild has identical bytes.

## 6. Important boundaries

- `source-intake` discovers/snapshots; it does not establish technical truth.
- `raw-index` verifies bytes; it does not judge whether the collector output is correct.
- Collector technical claims still require primary-source verification.
- New Raw files are allowed, but they must be intentionally added to the index.
- Existing indexed Raw files are immutable; corrections belong in normalized/evidence layers.
- A successful deterministic workflow never authorizes unattended publication.
- GitHub Release publication remains an explicit post-Freeze action.
