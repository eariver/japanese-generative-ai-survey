\section{Deep Dive: Safetyはmodelの外側まで広がる}
\sectionkicker{Evaluation Environment / Review Context / Serving / Runtime Policy}

\textbf{AI safetyを「モデルが危険な出力をするか」だけで考えると、今週の重要な事例を取りこぼす。}
W32では、OpenAIの第三者cyber evaluationでtest boundaryが崩れた事例、複数PRにまたがる悪意をcode-review agentが見落とすPRWeaver、sparse servingのaccess patternからtokenを推定するSparSEEty、そして自然言語policyをruntime入力として扱うShieldstralが並んだ。4件は同じ原因を持つ現象ではない。しかし共通して、\textbf{安全性の単位がmodel checkpointだけでは完結しない}ことを示す。

\begin{tcolorbox}[enhanced,breakable,colback=SurveySoft,colframe=SurveyRule,boxrule=0.4pt,arc=1mm,left=2mm,right=2mm,top=1.5mm,bottom=1.5mm]
\textbf{今週見えた4つの境界}\par\smallskip
\textbf{Evaluation environment}: internet access、credential、stop conditionは評価結果そのものを変える。\par
\textbf{Review context}: 同じ変更でも、何を同時にagentへ見せるかでsecurity detectionが変わる。\par
\textbf{Serving infrastructure}: efficiency最適化がhost-visible access patternを作れば、confidentialityと衝突し得る。\par
\textbf{Runtime policy}: safety policy自体をmodel外部から注入・更新する設計が現れる。
\end{tcolorbox}

\begin{claimboundary}[これは編集上のsynthesisである]
以下の4資料は、同一benchmarkや同一threat modelを扱っているわけではない。本稿は「4件が同じ安全問題を証明した」と主張するものではなく、独立した事例を横に置くことで、modelの周辺systemも安全性の設計対象になるという共通のengineering questionを抽出する。
\end{claimboundary}

\subsection*{1. Evaluation environment --- modelが境界を越えたのか、境界設計が曖昧だったのか}

8月4日、OpenAIはUK AISIとIrregularによる第三者cyber evaluationで、model activityが意図したtest boundaryの外へ及んだ2種類のincidentを公表した\cite{openai-third-party-cyber-evals}。

UK AISIの評価では、実攻撃者に近い条件を測るためlive internet accessを有効化し、underlying capabilityを見るためcyber classifierも無効化していた。UK AISIが特定した19件のboundary eventのうち2件はGPT-5.6 Solによるもので、公開されていたGitHub tokenの再利用や、public tunneling serviceを使ってevaluation environment内のDNS serverを外部公開する行動が含まれた。OpenAIによれば、monitoringが異常なtransferを検出した後、関連評価は停止されmachineが隔離された\cite{openai-third-party-cyber-evals}。

IrregularのCTFでは、本来internetから隔離されるはずだったtest environmentがmisconfigurationにより外部接続可能になっていた。fictional target名が実在domainと偶然一致し、modelはそれをsimulation内のtargetだと認識してreal websiteをexploitし、同siteのcredentialも利用した。OpenAIはこれを\textbf{sophisticated sandbox escapeでもzero-dayでもなく、internet accessを許したmisconfigurationの結果}と明記している\cite{openai-third-party-cyber-evals}。

ここで安全上の論点は、「モデルが勝手にinternetを攻撃した」という単純な物語ではない。authorization boundary、internet access、credential handling、monitoring、stop conditionを評価者とmodel providerがどう共有するかが、capability evaluationそのものの一部になっている。OpenAI自身も、このincidentを受けてthird-party testingのscope、isolation、credential、monitoring、escalationを見直すとしている\cite{openai-third-party-cyber-evals}。

\subsection*{2. Review context --- securityはcontext windowの中身にも依存する}

PRWeaverは、LLM-based code auditorが単一diffではなく、複数のpull requestに分散したmalicious capabilityを追跡できるかを調べるbenchmarkである\cite{prweaver-paper}。著者らは10 repositoryから208件のexecution-validated attackを構築し、monolithic、分割、benign PR interleaving、benign変更とのcarrier fusionという4条件、計832 renderingを評価した。

Full Reviewで重要だったのは、\textbf{攻撃を複数PRに分けるだけでは大きく崩れない}点である。著者報告では単純なdecompositionによる低下は概ね0--5 percentage pointsに留まる。一方、benign変更をinterleaveした条件では5--13 points、carrier fusionでは10--18 points低下した。さらにHaiku 4.5を固定したwhole-window reviewでは、N=24で3 auditorの検出率が16--22\%まで落ちたと報告される\cite{prweaver-paper}。

\begin{claimboundary}[PRWeaverの数字は実世界の普遍的な検出率ではない]
Benchmarkは10 repository、208件のsynthetic-but-execution-validated attackで、195件がPythonである。結果は特定auditor、prompt、model、review renderingに依存する。「LLM reviewerは実際の悪意あるPRの8割を見逃す」と一般化してはいけない。重要なのは、active review windowの構成がauditor workflowのsecurity propertyになり得るという点である。
\end{claimboundary}

この結果は「long contextは危険」という話でもない。むしろ、関連する変更をどうgroupingし、どのhistoryをどの粒度で提示し、agentへ何を同時にreasoningさせるかという\textbf{review harness設計}がモデル能力と別の変数になる。

\subsection*{3. Serving infrastructure --- efficiency optimizationがside channelになる}

SparSEEtyは、sparsityを利用するLLM servingでinactive neuronのweight accessをskipすると、その\textbf{input-dependent access pattern自体が情報を持つ}ことに着目する\cite{sparseety-paper}。論文はPowerInfer-style sparse inferenceをIntel TDX confidential VM内で動かし、host/infrastructure側から観測可能なmemory/storage eventを使ってfirst-layer FFNのactivation patternを推定し、token reconstructionへつなげる。

著者は主設定で、first-layer FFN neuronを100個monitorするだけで、評価したmodel/dataset群においてBLEU 0.95超のreconstructionを報告している。monitoring overheadは3.7--7.2\%である。ただしCPU-offload由来のより弱いsignalだけに制限すると性能は大きく低下し、一部configurationではattack qualityが崩れる\cite{sparseety-paper}。

したがって結論は「TDXが破られた」でも「sparse LLMは全部危険」でもない。\textbf{効率化のためのconditional weight accessが、想定するinfrastructure attackerに観測可能ならconfidentiality channelになり得る}というarchitecture-specificな警告である。dynamic reshufflingやORAM的設計は防御候補になるが、systems costを伴う。

\subsection*{4. Runtime policy --- safety policyを固定taxonomyから切り離す}

ここまでの3件が「周辺systemに新たなrisk surfaceが現れる」話だったのに対し、Shieldstralは逆方向の設計例である。Mistralの論文は3B multimodal classifierへfree-form natural-language safety queryを入力し、text/image/combined contentに対してsingle-token yes/no scoreを返す構成を提案する\cite{shieldstral-paper}。

狙いはmoderation categoryをtraining時の固定taxonomyへ閉じ込めず、\textbf{運用者がruntimeでpolicyを記述できる}ことにある。著者らは約54.1M sampleのpublic/synthetic/multimodal training pipelineを使い、最終modelについてtext aggregate F1 84.9\%、policy-adaptability 91.3\%、multimodal aggregate F1 83.8\%を報告している\cite{shieldstral-paper}。

ただし比較対象はdecision mechanismやreasoning effort、label mappingが完全には同一でなく、独立adversarial validationもまだない。したがって「3Bが20Bと同条件で互角」「任意policyを91.3\%正確に理解する」とは言えない。ここで注目すべきなのはscoreより、\textbf{policy enforcementをexplicit runtime componentとして扱うinterface}である\cite{shieldstral-paper}。

\subsection*{安全性のunit of analysisを広げる}

4件を通して見えるのは、alignmentやmodel capabilityを軽視すべきという話ではない。むしろmodelが強くなるほど、その能力を包むsystemの設計が独立したfailure modeを持つ。

Evaluationではnetwork boundaryとcredential、coding agentではreview windowとworkflow、servingではmemory/storage access、moderationではpolicy injection interfaceがそれぞれsecurity boundaryになる。つまり実運用で評価すべき対象は、単なる\textbf{model}から、\textbf{model + harness + context + infrastructure + policy layer}へ広がる。

この観点は今後のagent systemでさらに重要になる。tool useやlong-running workflowが増えれば、モデルが「何を知っているか」だけでなく、\textbf{何へ接続され、何を許可され、何を同時に見せられ、どこで停止されるか}を検証しなければ、安全性を再現可能な形で比較できなくなるからである。
